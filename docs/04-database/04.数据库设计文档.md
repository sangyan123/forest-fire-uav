# 森林防火无人机智能功能系统

## 数据库设计文档 V1.2

**项目名称：** 森林防火无人机智能感知、分析与闭环决策系统
**文档版本：** V1.2
**修订说明：** 本版本按《00 跨文档设计基线与矛盾修订清单》V1.3 第73章完成回写同步（2026-09-27），同步内容：media_type枚举统一、LocationMethod枚举、电量四级阈值、algorithm_config_version/dataset_version字段、权限字符串对齐。
**补充修订（2026-09-27）：** 修复 fire_track 保留字列名（timestamp→event_time）、fire_point 补 location_method 字段、新增 risk_area_assessment 评估历史版本表（对应00基线遗留缺陷清单）。
**数据库方案：** PostgreSQL + PostGIS
**缓存：** Redis
**消息系统：** Kafka
**对象存储：** MinIO / S3 兼容存储
**数据库定位：** 负责业务主数据、空间数据、算法结果、任务数据、审计数据及关键历史数据的持久化

------

# 1. 数据库设计目标

本数据库不是为了支撑一个普通无人机管理后台，而是为了支撑：

```
无人机
  ↓
原始数据
  ↓
标准化数据
  ↓
算法分析
  ↓
业务事件
  ↓
火情分析
  ↓
任务决策
  ↓
无人机执行
  ↓
执行结果

```

因此数据库必须满足以下要求：

1. 支持多品牌无人机
2. 支持无人机统一数据模型
3. 支持高频遥测数据
4. 支持 RGB/红外/视频等媒体数据
5. 支持 AI 算法结果
6. 支持火点和火场空间数据
7. 支持火情生命周期管理
8. 支持风险区域管理
9. 支持无人机任务与调度
10. 支持无人机控制命令与回执
11. 支持火势预测结果
12. 支持灾后评估
13. 支持全链路追溯
14. 支持模型版本管理
15. 支持未来 DJI/其他厂商接入

# 3. 数据分层原则

数据库采用四层数据模型。

## 3.1 原始层 Raw

保存厂商和无人机上传的原始数据。

例如：

```
DJI 原始 JSON
遥测原始报文
原始媒体元数据
设备原始状态

```

原则：

> 原始数据不可被业务逻辑覆盖。

将不同厂商的数据转换成平台统一格式。

例如：

```

 ↓

 ↓
uav_telemetry

```

## 3.4 业务层 Business


# 13.3 algorithm_task

用于记录一次算法执行。

```
CREATE TABLE algorithm_task (
    id UUID PRIMARY KEY,

    algorithm_model_id UUID NOT NULL,

    algorithm_config_version VARCHAR(64),

    dataset_version VARCHAR(64),

    task_type VARCHAR(64) NOT NULL,

    input_ref JSONB,

    status VARCHAR(32) NOT NULL,

    started_at TIMESTAMPTZ,
    completed_at TIMESTAMPTZ,

    inference_time_ms INTEGER,

    error_message TEXT,

    created_at TIMESTAMPTZ NOT NULL
);

```

注：

算法任务必须携带可追溯三件套：modelVersion（algorithm_model_id 关联的模型版本）+ configVersion + datasetVersion。

algorithm_config_version 为算法参数配置版本号，示例：fire-detection-config-v1.0。

算法参数的唯一来源为 config/algorithm/ 下的版本化配置文件。

------

## 为什么增加 position_error_radius

不能简单认为：

```
30.123456

```

就是绝对准确的位置。

应该：

```
中心点
+
误差半径

```

例如：

```
FirePoint
30.123456
114.123456

误差半径 = 8.5m

```

后续调度和核验可以利用这个误差范围。

------

## risk_area_assessment

保存风险区多期评估历史版本。risk_area 只保留当前态，同区域每次评估在本表追加一条记录，历史评分互不覆盖。

```
CREATE TABLE risk_area_assessment (
    id UUID PRIMARY KEY,

    area_id UUID NOT NULL,

    assessed_at TIMESTAMPTZ NOT NULL,

    risk_score DOUBLE PRECISION,

    risk_level VARCHAR(32),

    model_version VARCHAR(64),

    algorithm_config_version VARCHAR(64),

    dataset_version VARCHAR(64),

    factors JSONB,

    created_at TIMESTAMPTZ NOT NULL,

    UNIQUE (area_id, assessed_at)
);

```

注：

risk_score、risk_level 与 risk_area 同名同精度；area_id 关联 risk_area(id)，区域几何不在本表重复存储，需要空间查询时经 area_id 关联 risk_area。

model_version、algorithm_config_version、dataset_version 为算法可追溯三件套，factors 为本次评估各因子得分快照。

UNIQUE (area_id, assessed_at) 保证同区域同一评估时刻仅一条记录。

# 41. 常用空间查询

```
SELECT *
FROM uav_device
WHERE device_status IN ('ONLINE', 'FLYING')
AND ST_DWithin(
    current_geometry::geography,
    ST_SetSRID(
        ST_Point(:longitude, :latitude),
        4326
    )::geography,
    5000
);
```

这就是 F09 智能调度的重要数据库基础。

# 67. 最核心的数据库设计思想

整个数据库不是按照：

```
页面
 ↓
表

```

设计。

而是按照：

```
数据
 ↓
算法
 ↓
事件
 ↓
业务
 ↓
任务
 ↓
执行

```

设计。

其中最重要的一条数据链是：

# UAV → Detection → FireIncident → Mission → Command → UAV

这条链必须保证：

**可追踪、可回放、可审计、可重算。**

# 70. 最终数据库设计原则

项目数据库必须坚持：

```
① 原始数据不丢失
② 厂商数据和业务数据解耦
③ 算法结果可追溯
④ 空间数据统一 PostGIS
⑤ 高频遥测独立优化
⑥ 图片视频放对象存储
⑦ 任务与指令完整留痕
⑧ 火情全过程可追溯
⑨ 模型版本必须关联算法结果
⑩ 所有关键控制动作必须审计

```

# 71. 最终数据库核心闭环

```
无人机数据
   ↓

   ↓
Canonical
   ↓
Algorithm
   ↓
Detection
   ↓
Fire Incident
   ↓
Fire Point / Polygon / Track
   ↓

   ↓

   ↓

   ↓

   ↓

   ↓
```

这套数据库设计的核心不是“把数据存下来”，而是保证整个森林防火智能系统能够完成：

# 感知数据可进入 → 算法结果可落库 → 业务事件可追踪 → 决策过程可解释 → 无人机任务可执行 → 执行结果可回流。
